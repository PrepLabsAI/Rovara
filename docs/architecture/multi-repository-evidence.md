# Repository dependency facts

`EvidenceRaw.repositoryEdges` is optional. When a local multi-repository task saves evidence and the worker finds at least one dependency edge, it records `{ edges, notes }` alongside existing evidence. Edges alone never create an evidence file. Old records without this field keep their existing shape and bytes.

Each edge has `consumer` and `provider` repository IDs, `language` (`node`, `go`, `python`, `maven`, or `gradle`), and `source` (`base`, `candidate`, or `both`). There are at most 64 distinct edges, no self-edges, and at most eight fixed-word notes. Cycles are recorded as distinct directed edges; MR3 decides merge order. MR3 must check repository IDs against the task's pull requests before using the facts.

Edges are the union of the manifests at the workflow base commits and the candidate working files. A dependency removed from the candidate remains recorded with source `base`. **MR3/MR2b must NEVER use an edge's absence from the candidate to skip or narrow tests.** Every check continues to run in full in this lane.

**MR1 is on (`MULTI_REPO_CHECKS_LIVE = true` in `packages/worker/src/multi-repo-supplier.ts`, MR1-LIVE).** The worker derives once, lazily, under the first check round's existing timeout and abort/join guard (a derivation that runs out of that budget is derived again by the next round), and a local round with edges runs in MR1's check root. Single-repository, nightly, non-local and explicitly injected scopes retain their existing selection path. No-edge automatic rounds call the ordinary runners, create no check root or report directory, and emit no repositoryEdges field.

**Ignored files in the check root** (`packages/worker/src/multi-repo-dependencies.ts`). The check root is a checkout of the candidate tree, so git-ignored files are not in it. Before any check, every git-ignored entry of each repository is mirrored into its copy: installed dependencies (`node_modules`, workspaces included, and virtual environments), and also build output such as `dist/`, generated code, in-place built extensions and env files. Git lists them itself against the candidate snapshot's own index (`ls-files --others --ignored --exclude-standard --directory`). Every entry at the workspace root that is neither a repository, nor holds one, nor is worker state (`.agentx*`, `.rovara*`, `.git`) is mirrored too. Files are copy-on-write clones where the file system supports them (APFS, Linux reflink) and plain copies otherwise; hard links are never used, because a check writing a cache into a hard-linked package would write the workspace's own file. The sources are only read, through held directories. Go and Maven caches live in the user's home (GOMODCACHE, `~/.m2`), outside the workspace, and need no mirroring. The mirrored entries are added to each copy's own `.git/info/exclude` (as escaped literal patterns), so MR1's tree snapshots never take them in. Python bytecode caches (`__pycache__/*.pyc`) written by a check are not counted as candidate-source drift.

Link safety: a mirrored link that points into a repository or another mirrored entry is re-pointed at the copy. Once everything is mirrored, every mirrored link must resolve inside the check root. The only exception is a virtual environment's interpreter link (`<venv>/bin/python`, `python3`, `python3.N`), which must resolve to an executable regular file outside the workspace (the base interpreter) and is recreated to that exact file. A link out of the root, into the live workspace, or dangling refuses the mirror. Only after that check are a mirrored venv's script shebangs and editable-install files (`.pth`, `__editable__*`) re-pointed at the copy; only real directories are listed and regular files are opened without following a link.

Limits: the candidate tree keeps its 50,000 files / 512 MiB; the mirrored ignored entries have their own cap of 200,000 entries, 2 GiB and depth 64 per round across every repository (4,096 workspace-root entries). Mirroring is charged to the round's check budget.

**Original code.** In the automatic path, every original-code phase (TESTPROOF, SARIF baselines, measured befores) runs on today's path: the workspace itself shows the original code, as before MR1. MR1's check root could not show it faithfully when installed code outside the workspace (a Poetry or pyenv venv's editable install) points at the live candidate. When an earlier round ran in MR1's check root, the phase's fresh workspace reports are forwarded into a new worker-owned report folder for the phase, and the candidate's report root is restored when the phase ends, so no reader takes another round's report.

**Fallback.** Any refusal before a candidate round's checks run (a submodule, either copy limit, a link out of the copy, an unsupported entry such as a FIFO or a linked ignored folder, a repository not at its task branch or base such as an IMPLEMENT revert, or anything else), and a dependency wiring setup that fails on its own (for example Python without setuptools), falls back to today's per-repository path. The reason is recorded as a fixed note `multi-repo check not run: <reason>` in `repositoryEdges.notes` (with the derived edges) and as a progress note; it is never a silent pass or a false fail. The fallback is sticky for the invocation. A stop, an exhausted budget, an unconfirmed stop, or any error after a check ran never falls back. Known limits: a crash leftover check root with more than 8,192 entries makes the leftover sweep refuse, so that workspace falls back until it is cleared; a check that writes an unignored file other than Python bytecode (for example `.coverage` missing from `.gitignore`) is reported as changed candidate source and errors the round, as MR1 always did; the new note values need the contracts re-pin before a strict reader sees them.

Every parser step is linear in its input (no backtracking regular expression runs on manifest text); adversarial inputs are timing-tested. Automatic derivation supports root Node package dependency maps, Go module requirements, and conservative Python declarations. Python reads project name/dependency string arrays in `pyproject.toml`, literal metadata (`name`, `version`, `description`) and `[options].install_requires` in `setup.cfg`, and a literal `from setuptools import setup; setup(name=..., version=..., description=...)` form (with a newline instead of a semicolon) in `setup.py`. It never executes Python. Root `requirements*.txt` and `requirements*.in` files accept ordinary named requirements and sibling local/editable paths. Duplicate declarations, dynamic declarations, aliases, includes and unsupported syntax refuse the derivation as a whole with fixed words. Maven and Gradle remain tested separately. No lockfiles, nested manifests or installed package copies are read.

Limits are shared across the base and candidate: 32 repositories, 64 union edges, 2 MiB of manifest bytes within a 2.5 MiB total byte budget (including directory listings), 704 manifest reads, 4,096 root directory entries and 32,768 dependency items. Root inventories are bounded across every repository and both sources; an overflow refuses the whole derivation. Ambiguous provider names, malformed/unreadable manifests and exceeded limits yield no automatic scope; they do not change check verdicts. Manifest content and parser errors are never put into notes.

The contracts field must ship before or together with the emitting worker: an older strict engine schema rejects records containing it. Code ships worker and contracts together. The Cloud worker mirror, non-local execution proof, cross-repository selection/combined baseline (MR2b), merge ordering (MR3), and CI wording (MR4) are separate lanes. This behavior change must not merge before the controller's re-pin carries it.

## What the broker does with the facts (MR3b and MR4)

**Kept for the merge order.** When the broker keeps the evidence of a run, it also keeps the edges (consumer, provider, language, source; never the notes) in their own object `private/<owner>/<workspace>/evidence-pack/<task>/<candidate digest>.repository-edges.json`. It is bound to the candidate digest and the company (the blob store's own key), expires with the pack and is erased with the task's evidence. No edges, no object. A record that is not exactly what the broker writes reads as "unreadable", never as "no facts".

**Merge order.** `createRepositoryEdgesSeam` / `createTaskRepositoryEdgesSeam` (`core/merge/repository-edges.ts`) give `mergeOrderOf` the facts for the task's current code. A task with no facts is ordered, worded and digested exactly as before; unreadable facts and a cycle mean "no safe order" until a person confirms (DEC 209). Rovara never merges by itself.

**Watching (tracking pass).** A pull request merged by hand ahead of the one it depends on is said once, as a `stuck` milestone naming every pull request of the task. The pull requests that depend on the repository still waiting stay drafts until it merges (a pull request that is already ready cannot be put back). Nothing is taken back or merged.

**Shown.** The pull request description has a "Merge order" section (the order, and for a consumer the words that its own CI tests the repository alone and may fail until the repository it depends on merges); the task page shows the same lines, and a failing consumer's CI is explained. `MergeView.order` is added readers first (DEC 152a) and written only when `MergeDependencies.orderInView` is on. `MergePressBody.orderOverride` is the person's confirmation of an order Rovara could not check.

**Fix loop (MR4).** While a consumer's CI is failing and a repository it depends on has not merged, the CI fix slot decides nothing for it: that CI tests the repository alone, so the failure may only be the missing repository. Conflicts, feedback and syncs are untouched. Not built: re-running the consumer's CI after the provider merges (the code host port has no re-run call), so a failure that was only the missing repository can still enter the fix loop once the provider has merged (bounded by its three rounds).

## Cross-repository selection and one combined baseline (MR2b)

**Two-repository changes still run in full.** `MULTI_REPO_SELECTION_LIVE` (`packages/worker/src/verification/multi-repo-selection.ts`) is `false`; the selection below is built, tested and unreachable in production until a live proof turns it on. The plan field it reads is sent by nothing yet (the nightly is single-repository; a multi-repository nightly is the producer).

**The map names a repository for every path and every test** (`RepositoryCoverageMapSchema`, `packages/contracts/src/test-env-multi-repo.ts`): "this file of `lib` is touched by that test of `service`". At most one entry per (repository, path). The plan carries it as `repositoryCoverageMap` beside `checks[].repositoryId`, never beside the repository-less `coverageMap`, only to a worker that lists `task.testEnvMultiRepo.v1` (`featuresForTestPlan` adds it, so an older worker is refused the run at dispatch).

**Selection** (`planRepositorySelections`): a check selects only its own repository's tests (the same test id in two repositories is two tests). The check sees its repository's changes as they are, and the changes of every repository it depends on, directly or through others, under a key no path of its own can take. `selectTests` then runs underneath as it always has: a path the map does not hold, a stale map, a path that changes what every test means, too many tests selected, and a selection that picked nothing all run the whole check.

**The map is evidence of dependency too.** A file of repository P touched by a test of repository R makes P a provider of R's checks whatever the manifests say (a sub-package, an alias or a submodule is invisible to them). A provider's changed file that the map holds but no test of R touches runs the whole check: the map may simply not record coverage of the provider's files from R's runs.

**What may be skipped.** A changed repository that the check's repository does not depend on is ignored only when BOTH are fully known. `deriveRepositoryFacts` (`multi-repo-edges.ts`) returns the edges (exactly `deriveRepositoryEdges`' union of base and candidate) plus `complete` and `unknown`. A Maven or Gradle manifest in either source, or no manifest of a supported language at all, makes a repository unknown: it may depend on anything, so its checks, and the checks of every repository whose change might reach it, run in full. An ambiguous name, an unreadable manifest, a limit or an abort is `complete: false`: every test check runs in full. **An edge the candidate removed or added still relates the repositories; absence from the candidate never skips a test.** Declared globs and the import graph are one repository's, so with two repositories only the coverage map selects.

**One combined baseline.** For a task with two or more repositories the worker finds, before any check runs, each repository's nearest offered trusted commit (`findBaselineAncestors`, one time limit for all, sorted by repository). The engine asks for it with `plan.repositoryBaselines` (set with the candidates for a project of two or more repositories; a worker that was not asked writes no `baselines`, so an engine without MR2b never sees the field). The claim (`EvidenceRaw.baselines`) exists only when EVERY repository has one and no commit is claimed twice. The engine (`combinedBaselineFor`) looks each part up with `baselineFor` and builds the combined baseline only when the claim is for exactly the project's repositories and every one has a usable row of one kind of writer on the task's branch; the stored words (`EvidenceBaseline.repositories`) name each repository's commit and the line says so. The rows' failing sets are repository-less, so a combined baseline excuses no failure (`alreadyFailingFromBaseline` gives nothing for it). With fewer than all repositories there is no baseline: today's behaviour. No producer writes rows for several repositories yet.

The new contract fields must ship before or together with a worker that emits them (strict schemas); the Cloud worker mirror will not emit them.
