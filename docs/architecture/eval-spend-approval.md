# Setup eval spend approval

`setup-eval-spend` is a separate high-risk DecisionGate subject. The existing setup-command digest, candidate check, subject order and owner-only gates keep their meaning. The local setup page displays a staged eval item and its own form, bound to its revision and digest, before approval. Approving it records permission; it does not launch a health check.

A trusted setup host calls `proposeEvalSpendApproval` with the discovered eval selection, F3d's whole three-run estimate (three × question count × the per-question call/cost bounds), immutable eval inputs and suggested budget. It must not accept these as authority from request JSON, repository settings or model output. The host supplies the scorer/judge pin, eval-set hash, exact model/version/catalog route, command fingerprint and measurement settings fingerprint. The record retains the approving identity and its role at approval time. `Approvers.verify` authenticates the person; the broker checks live `SessionMembers.companyRole` and, for a company member, `SessionMembers.projectGrant(person, project)`. Owners and admins remain company-wide; a maintainer of another project, a member without the grant, an auditor or another company cannot approve. Hosts must inject the same members seam into decisions, proposals, views and capabilities. The local decision default is `localOwnerMembers`; the local page resolves only its authenticated install owner. Local install sessions remain owner-only. Cloud's setup screen consumes this after its Code re-pin.

The independent digest binds the company, project, selection, full input identity, whole estimate and both the usual and maximum project budget. The eval-input digest omits the code commit so a background refresh of unchanged eval inputs can use the same approval. More calls or cost, different eval inputs, selection or configured budget requires re-approval. Default maximum: 400 calls and 4,000,000 microdollars ($4), shared with eval-round; general task budgets are unchanged. The trusted host must supply the effective company/project `monthlyCapMicros` when proposing; a missing, invalid or smaller cap refuses the proposal with fixed words. This cap is the configured monthly ceiling, not its remaining balance; the reservation adapter still checks live remaining spend. Views only say “within the monthly cap” when their supplied current cap covers the maximum. The approval is persistent without a time expiry, as DEC 194 permits recurring refreshes. Current authority is checked on every read/reservation, not inferred from the historical role. If the approver loses the required role, the view says “approval needs renewing”; proposing the same plan writes a fresh waiting revision and asks again. An unreadable membership lookup also fails closed. The stored schema and digest format are unchanged.

`createEvalSpendCapabilities` produces the F3d `EvalSpendApproval` and `MonthlyMeter` ports. It validates the stored record/digests, re-reads current inputs and current company/project membership and customer connection, and issues a frozen in-process grant. The meter accepts only its own grants, validates the whole requested estimate, and revalidates the unchanged approval. The worker independently compares its actual eval-input digest and refuses an incompatible grant before reserving or running.

The **injected trusted `EvalReservationAdapter`** owns money and provider scope. It must atomically hold the whole estimate within company/project monthly caps and the approved project budget, revalidate authority/approval inside the hold and at dispatch, issue its own opaque customer-provider scope, and charge each call against that hold. Per-call accounting must consume the hold without double reservation. It must bound/join calls, account for failures, and release only unused known spend on close. No repository-supplied payer or fallback to Rovara's provider exists.

No production adapter is bound here: **F3E-RESERVATION-BINDING-IN-F1E** belongs to Cloud F1e. This lane neither copies a meter nor changes F1c LocalMeter/payer interfaces. With no adapter, missing/revoked approval, stale digest, changed inputs, higher estimate, missing provider or failed reservation, health returns `Not run` with zero calls. Automatic trusted discovery/estimate delivery and refresh scheduling remain host integration seams from F3d; the persisted setup item, decision path and capability producers are available here. All tests use fakes and no real provider requests.

Approval storage uses one company/project setup row (`EVAL_SPEND`). Corrupt records mean no approval and emit only the fixed event `eval_spend_approval_invalid` (through the injected log hook or the default warning logger). A fresh proposal can replace them, guarded by the raw snapshot and absence of missing decision fields; recovery uses a fresh random revision so historical decisions cannot be replayed. Proposals read the row once and condition on the previously read snapshot; decisions use the existing DecisionGate transaction for the subject update, audit and replay receipt. A stale form or race cannot replace an intervening approval. The existing setup records are not migrated or reinterpreted. Page costs use two decimal places. Page copy contains fixed words and validated finite amounts; repository labels and provider errors are not displayed.
