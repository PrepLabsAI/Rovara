# Company inventory (R4, public Code / code/next)

All nine company-separation parts T1–T9 must pass before the pilot. This inventory is a migration baseline, not proof that Code already isolates every company.

Record kinds are groups of static entityType and partition-family identities (including canonical imported builder identities); associated identities share a row. Every scanned identity appears exactly once. Unproven/mixed families stay needs-company even when one caller is safe. This conservative classification deliberately does not infer safety from a name. Questions in those rows belong to T1.

The route total includes both dispatch patterns and the separately identified API Gateway route keys below. Prefix dispatch literals are included as patterns. Methods are hand-maintained: adding a METHOD on an existing path is NOT caught by this inventory. A checked=yes row proves only its explicitly named entry in COMPANY_CHECKED_ROUTES, and only with the optional membership reader enabled. Mixed-method or downstream-unproven rows remain needs-company. Core handleTaskRoute trusts its principal; other developer routes, admin, Slack and GitHub paths remain needs-company (T2).

Generic key/field forwarding rows are separately enumerated below and **excluded from the record-kind count**. Their file:line:column:field and exact expression form a ratchet: a new, removed, moved or changed site fails the test until reviewed. Imported constants and aliases use compiler symbols; unreadable constructors, unresolved sites and parse failures refuse the entire inventory. Source is read once under one total file/byte/item/node-visit budget (4,000 files, 40 MB, 100,000 identities/directory entries and 10 million traversal steps); the test runner retains its timeout; tests never read git history.

## Round 2 bounds and compatibility

Core workspace operations permit **10 reads**, each requesting at most 200 rows and limited by DynamoDB to a **1 MB page**, followed by one 1-row completion probe. Large rows can exhaust the read bound below 2,000 operations. The whole operation read refuses if the probe finds more; no partial operations are returned.

Checked task lists admit at most 2,000 items across SDK and task-action results per call. A result crossing that budget ends the page before the unfinished task; the exclusive-start cursor names the last fully examined index row. The crossing result is not used, still counts toward the 8 MB/512-command/10-second limits, and prevents further reads. A task too large to complete even on a fresh page still refuses with fixed words. Other limit failures remain refusals; shared workspace reads stay cached per call.

### Replaces

The prior blanket claim of byte-identical lists for implicit-company members with the check enabled is replaced by these exact exceptions, pinned in six filtered goldens (checked and legacy):
- Project/status filters: checked lists examine at most the requested `limit` index rows, instead of the legacy 200-row scan. A filtered-out row can produce an empty/short page with `nextCursor`; following it reaches the remaining tasks.
- Stale index timestamp: checked lists return the canonical task view's `updatedAt`, while legacy lists retain the index value unless status changes.
- Aggregate item bound: checked lists now return completed tasks plus continuation instead of the former 400 refusal when a later task crosses the budget. No task is skipped or partly returned.

The membership-absent path and the seven original golden pairs keep their response bytes. These exceptions do not enable the check or add company writers (T2/T3).

## GitHub installation operator runbook (T5)

Only an install operator with existing direct broker Lambda invocation permission may run these events. They have no HTTP route; company-admin tokens and HTTP-shaped invocations cannot claim. Keep the optional binding and membership dependencies behind the staging/review gate. No IAM or infrastructure change is included here.

Before backfill, inspect the GitHub App's installations and confirm which belong to the implicit company. Freeze installation changes while walking pages. **Bind the pilot company's installation with `agentx.github-binding-claim`** before backfill if it already exists, or after backfill if it is installed later. Backfill preserves explicit bindings and assigns only validated unbound installations to the implicit company. It cannot infer a company's ownership from a GitHub account name.

An operator invokes the existing broker Lambda with this payload (substitute verified positive installation id and company id):

```json
{"source":"agentx.github-binding-claim","installationId":77,"companyId":"org_aaaaaaaaaaaaaaaaaaaa"}
```

The broker verifies the installation through this App's GitHub credentials, then atomically writes its conditional binding and `AUDIT#CLAIM` record. A second claim, including the same company, is refused. Unknown, foreign, invalid and already-bound requests have the same fixed refusal. `boundBy`/audit actor is `operator-lambda`; Retain the operator invocation evidence to identify the IAM caller. Never try to reassign an existing binding with a raw table write. Later T3/Cloud self-service must verify WITH GITHUB that the person administers the installation account.

Next invoke `{"source":"agentx.github-binding-backfill"}`. Each call makes one installation-list request (25 rows, 1 MB response, 5-second HTTP timeout), no repository/token fan-out, then at most 25 validated binding writes under a fresh 304-command/1 MB/10-second store budget. On `more:true`, invoke again with the returned numeric `continuation`. A persisted page checkpoint refuses skipped pages. A full page requires a following page; only the final page seals the completion marker. On a failure, retry the same page; inspect the saved progress if a successful response was lost. Confirm `more:false`, the marker, implicit bindings and the pilot binding before enabling any second company.

Recovery similarly returns `more:true` and an opaque `continuation` when bounded listing stops. Invoke `agentx.github-webhook-recovery` again with that exact continuation until `more` is absent. Each call lists at most 50 companies and processes at most 100 deliveries (25 rows per company page). Registry/partition reads alone spend the shared 512-command/2,000-item/8 MB/10-second budget; processing uses the plain client and existing expiring delivery leases. Listing stops before claiming any unfinished page. Invalid legacy rows are skipped and counted in `skipped`; inspect and repair them under the owning company's authority. Other company partitions still run.

Bindings absent retains the existing webhook/recovery response bytes. With bindings present and membership absent, retry fails closed. Legacy administrator registration/retry identities without a checked developer identity also fail closed; the authenticated client creation path supplies its checked developer id.
