# Eval in the final check

The broker's `eval_hint` adds an optional CHECKS request. Delivery drops it, with a fixed log event, for workers without `task.evalRound.v1`. A request carries the pass number and prior task usage. No request preserves the existing CHECKS path.

After ordinary checks, evidence capture and test proof, the worker calls `runFinalCheckEval`. Its guards are ordered: connected ports, trusted fresh round kind, verified tests, readable trusted plan, then a matching confirmed customer grant. Company, project, selection and the eval-input digest must match. A project with no configured eval takes the existing no-eval notice path before reading approval. A baseline already being measured returns immediately.

`openMeteredStage` reserves the whole next stage and counts its own dispatched calls and returned costs. Runner-reported usage is not authoritative. A refused hold maps to the fixed budget refusal. Reservations close after pending calls join, including errors and cancellation. A cold baseline and comparison share the remaining task budget, including prior attempts; the same validated grant is reused. Unknown cost prevents further spend. This module neither builds a meter nor chooses a payer.

The eval shares the original CHECKS deadline and abort signal. The existing bounded abort/join guard marks the workspace unsafe if stopping cannot be confirmed. No candidate reread follows an unsafe stop. A completed Worse result survives cancellation of a later stage or a failed reservation close; unknown cost prevents further spend. A failed model call cannot supply comparison facts. After a safe return, the candidate is reread so eval-created drift is visible to the broker.

## Evidence and downstream consumers

`eval-round.json` is bound to the pre-check candidate digest. It stores actual comparison pass bits, bounded differing answers, usage, fixed notice codes and bounded feedback. Private evidence contains only pass/fail or a fixed refusal, with the binding envelope. The strict writer and tolerant reader live in contracts. `evalResultFromArtifact` is the only downstream verdict function; stored labels, summaries and feedback never determine the verdict.

The broker reads at most ten task operations, 1,000 listing entries and one MiB total under the existing proof-read timeout. Object keys must belong to the owner, workspace and operation. Parse or accounting faults refuse the whole read. Prior failed attempts consume budget too. Truncated history, an orphan completed second pass, or a requested attempt without a saved artifact cannot authorize more spending. Ordinary operations without an eval request or artifact consume no eval budget.

The PR-evidence lane should use `loadEvalRound` and `evalResultFromArtifact`; the first-task-during-setup lane should feed that same result to its not-tested entry. This lane does not render PR text, change draft/Proven policy, or drive the single fix round. The artifact carries `feedback` and `fixRequested` for that later driver.

## Host composition (plan v3.2 row 20.2)

`createEvalFinalCheckPorts(capabilities)` (worker, `verification/eval-host.ts`) composes the ports from one injected, trusted capability set and binds nothing when any capability is missing or not a function (the request then reads `not_connected`, zero calls). `main.ts` now binds it per task through `evalFinalCheckForTask` (`eval-wiring.ts`, below); the trusted sources it needs are not delivered on this base, so a task still reads `not_connected`.

- `modelAccess: EvalModelAccess` (`eval-model-access.ts`). `hold({grant, calls, costMicros})` holds the WHOLE stage estimate and returns an egress, an opaque scope and a `release`. `createEvalMeter` turns it into the `MonthlyMeter` the eval consumes: a call beyond the held count, or once settled spend has reached the held cost, is refused before the egress (spend is only known when a call settles, so at most four calls are open at once and the rest wait; the gateway enforces the hold itself: it must reserve per call, refuse once spend on the hold reaches the held cost or count, and pass it by at most one call, flagged `overrun` on that call's settle, the DEC 165 pattern); a call refused because the held count or cost is used up is Not run `cap` with the cost still known and is not counted in usage, while any other fault is an unknown cost; each call is one attempt, never retried; a thrown fault, a malformed or over-long answer (10 MiB) or a deadline (2 minutes) is `provider_error` with an unknown cost, so the stage stops and the spend is retained; an overrun settle stops the stage; `close` joins every call and releases only known unspent spend. A rate limit, quota, overload, refused key, gateway cap or provider error keeps its own Not run reason and is never a pass or Worse. Production: the gateway's product route, reached with the task token Code mints (`/v1/internal/model-access`). Tests: a script.
- The production `EvalModelAccess` is `createEvalGatewayAccess(gatewayUrl, tokenSource)` (`eval-gateway-access.ts`), written against the gateway's published eval-hold contract only (Gemini; Vertex is a follow-up). `hold` posts `{grant (its nine fields), calls, costMicros}` to `/v1/product/eval/hold` with the task token as `x-api-key`, and uses the answer only when it is a 200 with a readable scope and exactly the asked calls and cost (another amount is released at once, unspent; anything else holds nothing). Each call goes once to `/v1/product/gemini/<path>[?alt=sse]` with `x-rovara-eval-scope`, only `generateContent`/`streamGenerateContent` paths and only the `content-type`/`accept` headers; the NDJSON answer (one head, base64 chunks, one settle) becomes the egress events. A non-200 or non-NDJSON answer, a fault after sending, an abort, or a malformed, over-long (16 MiB) or settle-less stream throws one fixed fault, which the meter reads as `provider_error` with an unknown cost; the stage then sends nothing more and the release says `unknown`. As a second line to the gateway's hold rule, it sends nothing once its known spend reaches the held cost, its count is used or an overrun settle arrived, and flags `overrun` on a settle that takes its known spend past the hold. `release` is posted once, with the larger of the meter's and its own count and spend (`unknown` when either lost a cost or a call is still open); a failed release is not retried (the gateway settles the stage at expiry at its own counted spend, the whole hold if a call is still open). A hold whose answer was lost (a fault or timeout after the gateway made it, an unreadable scope) cannot be released and waits for that 4-hour expiry. Redirects are never followed. `evalFinalCheckForTask` builds it for a task (below).
- `exec: EvalSandboxExec` (`eval-runner.ts`). Runs the confirmed eval command for one side in the check sandbox and receives only an egress (every call is the stage's metered `call`), an opaque scope, the ids, the run count and the signal; never the reservation, grant or a key. Its result is runtime-checked, and a round where the stage refused any call or the stop signal fired is never a result, whatever the exec wrote (a stage asked for more calls than it was held for is Not run, over budget); its own accounting is ignored; a plain object is not an attestation; the new side carries none. Production: `createBridgedEvalExec` (`eval-bridged-exec.ts`): the F1-c bridge over the stage's egress and a `FreshEvalSandbox` (below).

A finished comparison also records its basis in `eval-round.json` (`basis`: eval-set hash, judge pin, model, model version, three old runs), and `evalProofBasis(artifact)` (contracts) re-derives the proof row from the bits: cases passed (old and new), the slices (ordinary, safety, refusal), the baseline, the judge and the bar (`EVAL_PROOF_BAR`). A stored label never decides any of it; a private-set round has no row.

## Host binding contract

Only trusted worker wiring may supply `EvalFinalCheckPorts`; `main.ts` binds it through `evalFinalCheckForTask` and nothing else. The host must:

- derive the plan, round kind and public question inventory from trusted confirmed setup and the actual check sandbox (this plan does not mount a private set);
- supply company-scoped approval, cache and reservation capabilities, with a single authority for reserve/call/close;
- run old code with a valid Rovara baseline attestation and produce complete bounded per-question reports;
- charge every model call through the supplied call function, honor abort, impose provider deadlines, and join the sandbox and all calls before returning or rejecting;
- preserve workspace safety errors and never resolve while a writer remains active.

Until the sources below are delivered, requests produce `not_connected` and spend zero. A working or unknown sandbox produces `needs_fresh_sandbox`. The laptop adapter and the move of laptop final checks into a fresh CHECKS round are separate work. Cloud binding waits for the company/project meter and fresh check round. The real-model-test lane can reuse the metered stage and append its own independent final-check step. Integration follows the eval approval/health stack and the 0.5.18 re-pin.

## Task binding (live wiring)

`main.ts` calls `evalFinalCheckForTask` for a task that carries an `evalRequest` and passes the answer to `runTaskInvocation` as `evalFinalCheck`. The answer is undefined, and the request reads `not_connected` with zero calls, unless all of these hold:

- **The host switched it on.** `ROVARA_EVAL_GATEWAY_URL` is the model gateway's https origin (no path, credentials, query or fragment). Unset, or anything else, is off. Off is byte-identical to before this binding.
- **The trusted sources exist** (`EvalHostSources`: plan, approval, cache, baselines, a `FreshEvalSandbox` and the run folder), built per invocation from its own capability and company (`evalHostSourcesFor`). On this base none is delivered, so `evalHostSourcesFor` answers undefined; the plan, the approval and the baseline cache are the control plane's, and the fresh check sandbox is TE-B1. The worker supplies the changed-prompt classifier locally, below.
- **A fresh sandbox is available.** Without one the round kind is `working` and the request reads "needs a fresh sandbox" before any token is asked for or any hold is made.

**One model route.** The eval's model calls go only through the gateway's product route (`createEvalGatewayAccess`). The task token is the key the control plane mints for this operation (`GET /v1/internal/model-access` with the operation's own callback capability). It is sent only to the origin it was minted for: a `baseUrl` that is not the configured gateway's origin (an install with no gateway, a proxy key, another port, http) is never sent anywhere, and the eval is Not run. The token never enters the sandbox, an artifact, a log or an error.

**The exec.** `createBridgedEvalExec` makes one F1-c bridge per run, listening on a Unix socket in a private (0700) folder of its own; its egress is the stage's metered `call`, so every call is held, counted and bounded by the stage. The sandbox gets the socket path and one token made for this run (`check_unsealed`, forwarding mode only); the token is dropped, the bridge closed and the folder removed when the run ends, however it ends. The bridge's own call limit is raised to 10,000 so the stage's exact hold, not the default 200, is the line that decides. The changed prompt is counted by the worker's own classifier on settled-ok calls only, never on the sandbox's word. Only an explicit false excludes a call; an absent, malformed or throwing classifier counts it as changed.

**Changed-prompt classification (EVAL-WIRE-CHANGED-PROMPT-CLASSIFIER).** The CHECKS hook scopes a classifier to its invocation with `withEvalChangedPromptClassifier` (`eval-changed-prompt.ts`); `evalFinalCheckForTask` uses `evalChangedPrompt` as the default producer for `EvalHostSources.changedPrompt`. Source reads share the check's abort/deadline and use the same pinned base and pre-check candidate tree as the evidence binding. Isolated Git reads a bounded raw object diff with no rename inference, external diff or textconv, then the full regular-blob sides by object ID. F4's existing `detectPromptChanges` supplies coverage and change identities; F8's `planRecording`, `readModelRequest` and `matchChangedItems` supply request parsing and fingerprint matching. No new detection rules, wire fields or record kinds are added. Text stays in worker memory and is never logged or included in evidence.

A readable prompt call with a complete F4 `none_found` report is unchanged, so an unrelated-code change retains zero changed calls and the existing Not run result. An F8 fingerprint match is changed. Every undecidable case also counts as changed: unsupported files, unreadable or oversized source/diff, non-regular blobs, incomplete/truncated reports, missing/mismatched base identities, missing check context and unreadable frames. A non-match is not evidence of an unchanged source, unless F4 reports a complete `none_found`. Known limit (EVAL-PROMPT-DETECT-RUNTIME-LOADED): F4 does not see a prompt the code loads at run time from a file whose name and kind it does not recognise as a prompt (for example `assets/persona.txt`), or from a string constant in a module with no AI import; such a change reads `none_found`, so the eval reports Not run (never a pass). The diff base is the candidate repository base; until the eval plan is delivered it is not tied to the plan base commit (EVAL-WIRE-CLASSIFIER-BASE-BINDING). Multi-repository path collisions conservatively make the report incomplete. Async check contexts do not share classifiers across invocations or companies. Sandbox headers, body claims and result accounting never decide the count; conservative classification still passes through the existing approval, model pin, budget, question-report and verdict guards.

**Any outage is Not run.** A refused capability, an unreadable access answer, a gateway down at the hold or mid-stage, a sandbox that fails, a stop: each is a fixed Not run reason with the spend accounted (a lost cost is unknown and retained). The honesty guards are unchanged: no outage is a pass or Worse.

**Still to build before a first real run** (each reads Not run until it exists): the trusted plan and question inventory, the persisted approval and the company-scoped baseline cache delivered to the worker (EVAL-WIRE-SOURCES-NOT-DELIVERED); the fresh check sandbox with the model helper and the base-commit attestation (TE-B1, `FreshEvalSandbox`); and the gateway accepting the operation's task token on the product eval routes.
