# Company project catalog rollout (controller only)

## Which companies need this (company partition is authoritative)

The settings compliance list (S3) reads a NAMED company's own partition directly: ORG#<company>#PROJECT_CATALOG and the selected ORG#<company>#PROJECT#<name> REV# row. No flag and no backfill are needed for it. Rows there may omit companyId (Code's own writers and the switch-over move do); a row naming another company is drift and fails closed. This is the layout staging has after the switch-over (2026-11-17 discover: 0 shared rows; one company's 15 catalog and 31 revision rows, no companyId).

The steps below remain only for:
- the implicit company (org_00000000000000000000): its legacy projects live in the shared catalog, and its S3 list and D1 forward writes switch to the partition only once it is verified and marked;
- copying a named company's legacy shared rows (if any, from before L4 forward writes) into its partition with L4. Such a company needs no mark: once the copy is applied its S3 list shows them. verify (without --mark) is the consistency check; partition-only projects are reported as `extra`, not refused.
`--verify --mark` refuses a named company (invalid_input). A flag row left on a named company is ignored; `--unmark` still removes it.

PR A+B adds no scheduler or automatic migration. Keep the staging operator guard, us-west-2 region, explicit table names and the runner's 5-second/500-command/500-item/2-MB budget. Run the commands below through the existing operator guard, never from a web request. All commands default to preview; only --apply permits database writes. The input must be a regular JSON file, not a symlink (O_NOFOLLOW, maximum 64 KiB).

1. Staging discover: create a separate output directory and a JSON input containing `{}`. From the built worktree, invoke `node packages/broker/dist/aws/core-backfill-runner.js` with `--state-table <state> --signin-table <signin> --input <discover.json> --discover`. Review the per-company indexed/missing/conflicts report, including the implicit company's older unattributed projects. Nothing is copied here. Follow the table-bound --continuation until exhausted; generated mapping files have a page-specific name and are created exclusively beside the input. A conflict suppresses that company's mapping for the page. Review every page before any apply, including mixed-company historical revisions. Do not infer ownership from a caller or supply a different company for unattributed rows.
2. L4 phase 0: use each reviewed mapping file (at most 100 project names), an explicit unique --run-id, and no action switch. Preview first. Repeat with --apply only after review. Continue each bounded page using its continuation and the same mapping, table names, run id and preview/apply mode. A preview continuation cannot be applied. Retain every report; any conflict or unavailable result needs correction before continuing. L4 copies every historical revision into the company partition as well as the catalog pointer (D3), uses snapshot fences, leaves legacy rows untouched, and tags only rows created by the run. That company's own older repositories become available to its core code host. Repeating the apply is idempotent.
3. Verify one company: input is `{"companyId":"<company>","runId":"<run>"}`. Use --verify, then --verify --mark to preview marking, then --verify --mark --apply. Marking requires the history names and company partition to match exactly, every historical core copy to match, and the selected core revision to belong to the company. A newer core setup approval is retained. Every difference produces a report and no write. The flag uses attribute_not_exists and catalog snapshot fences in the same transaction. A company already flagged cannot be re-marked. The atomic mark is limited to 99 catalog rows; larger or over-budget verification refuses without writing. Do not split one company's flag verification into subsets.
4. Watch `project_catalog.index_drift` for 24 hours. The event carries only the served company id; drift returns the fixed settings-unavailable response. Then repeat for all eligible staging companies, and repeat the same discovery/review/apply/verify/observe sequence on production. A company's old v1 cursor is refused once its list moves to the partition (named companies: on deploy of this change; implicit company: at mark); clients restart from page one.

Rollback: --unmark <runId> previews the conditional flag deletion; --apply performs it only if the stored run matches. The company's next read immediately uses the unchanged shared/v1 path. The catalog retains a mark receipt, so unmark does not enable a later destructive undo. Before a company has ever been marked, --undo-run <runId> previews and --apply deletes only that run's newly created catalog/core rows, atomically with an absent-flag check and snapshot fences (maximum 99 deletes). Existing rows, another run/company and legacy data remain. If later core work depends on the copied revisions, undo refuses. It never drops a subset silently.

PR C and closing DEC 253e wait for the controller to verify the implicit company. The legacy scan and v1 remain only for the unflagged implicit company. A refusal caused by the total budget or atomic transaction ceiling needs controller planning; never bypass the checks or mark by hand.
