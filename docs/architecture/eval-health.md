# Eval discovery, health and baseline refresh

This Code seam implements setup measurement with trusted injected capabilities. It has **no production approval or monthly-meter adapter**. An unwired call refuses without making a model call. The existing broker confirmation body and approval digest are unchanged. The separate setup wiring lane must supply a persisted eval selection, a new explicit confirmation item/digest entry, current maintainer/admin authorization, and a customer-provider capability.

`evaluateReadiness` accepts an optional `evalSetup`. It discovers report/config/folder candidates through the existing A4 reader and returns inert labels. Discovery does not execute configuration, pick a candidate, grant approval, or infer question counts from config filenames. A measures report without question rows is explicitly aggregate-only. Incomplete inventories report omissions instead of claiming no eval exists. Folders, configs and reports within an eval container are grouped at its direct child suite roots (for example `evals/refund`); nested fixtures/results do not become separate choices. Config/folder candidates require the trusted setup adapter to enumerate the confirmed eval's questions and support re-asks. The later UI owns confirmation and pointing to a different eval; this lane adds no button action.

`runEvalHealth` requires `EvalSpendApproval` and `MonthlyMeter`. The former reads persisted selection, current role/connection and the confirmed estimate. The latter atomically reserves all three runs within the company/project monthly cap, resolves its own opaque ModelEgress scope, and meters **every call, including provider errors**, to the customer's provider. Neither a repository nor a runner supplies company/provider identity. The adapter must enforce the reservation at dispatch and retain uncertain spend. The worker also counts dispatches, requires an explicit `ok` ModelEgress outcome, and checks reported usage; it closes and joins the reservation before saving a baseline. The shared DEC 203 eval defaults are 400 calls and 4,000,000 micro-dollars for all three runs together. Larger limits require both an explicit limit and a sufficient confirmed estimate. Refreshes use the same approval within these limits.

The injected runner runs only the resolved main-branch checkout, with the working sandbox paused; it reads fresh A4 measures and returns the runtime-branded checkout attestation. All product and judge calls go through the provided `call(frame)` function. It must join its work before returning, preserve the pinned model version and judge, and produce exactly one sample for every confirmed question per run. No key, raw error, response header or stdout is part of health output. The meter's response events are already scrubbed ModelEgress events. Missing/invalid results cannot fill the baseline.

Three complete runs yield question count, mean pass rate, differing answers/pass outcomes, actual calls and seconds for each run, and per-question support. Failures in these old-code answers are measurements, not refusals. The baseline saves all three question samples. A storage refusal leaves the measured result visible and says it could not be saved.

Sensitivity is an **estimate**, not a gate or certainty claim. It runs F3c's exact whole-set rule, fresh suspect re-asks and second look on 256 seeded independent-question simulations. Three observations per question use Jeffreys smoothing `(passes + .5) / 4`, including apparently steady questions. The simulated drop removes pass probability from the strongest questions first, down to .02, until the requested pass-rate drop is reached. The reported threshold is the smallest tested five-point step with at least 80% catch probability. Additional-question estimates test doubled sizes up to 1,000, assuming comparable new questions. A null result says the target was not reached in the tested range. Estimates never promise a drop larger than the measured passing share; an all-failed baseline has no passing answers left to lose. This scenario differs from a guarantee for arbitrary regressions, correlated questions or cached providers. The no-change simulation is a test; the existing F3c simulation remains the statistical regression gate.

Dependency-keyed cache records use a v2 key: company/project, eval set, hidden-set identity, command, catalog/model and exact model version, settings, judge pin, and a trusted hash of **all code files**. The producer must hash all code bytes and paths; a conservative hash of all tracked files is acceptable. It must never use a repo-reported hash, a partial path list, mtime or the commit as a substitute. `baseCommit` still binds the writer's attestation, but changes in commit identity alone do not invalidate an otherwise identical v2 key. Legacy inputs without both new fields continue to use their v1 per-commit key and existing reader. New health runs require v2 identity. Expiry remains checked on read at 30 days maximum, stored in seconds.

`createEvalBaselines().afterMerge(input)` is the host's post-merge/setup refresh hook. Cache hits do no work; changed code, eval, judge or model causes a miss. The host owns and joins this promise on shutdown; the module starts no timer, process or detached job. `forTask(input)` returns `measuring` while that identity is in flight, otherwise reuses the cache or measures a missing baseline. Wire this into `EvalRoundInput.prepareBaseline` using the key passed by the round and the same trusted image/route settings; setup, refresh and task comparison derive the settings fingerprint with `evalSettingsFingerprint`; the task then re-reads the saved record before comparing. Its notice says `baseline still being measured` without holding the first task. Private-set task feedback remains fixed words and does not expose measurement details.

Live setup delivery, trusted hash inventory production, customer adapter construction, and invocation of the post-merge hook belong to the separate production wiring lane. Tests use fakes only; nothing here authorizes a production model call by itself.
