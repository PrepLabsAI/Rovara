# Asking a company rules service (policy hook)

An install that works for a company can name the service that holds the company's rules. Rovara then asks that service before work starts and before a person decides, and the service can only make things stricter.

## Setting it up

Set the `CorePolicyHook` stack parameter (passed to the broker and the dispatcher as `ROVARA_POLICY_HOOK`) to a JSON object, for example `{ "address": "https://rules.example/v1/policy-hook", "jwks": "https://rules.example/.well-known/jwks.json", "thumbprints": ["<RFC 7638 SHA-256 thumbprint>"] }`. Each URL must be HTTPS with at most 200 characters and pass the policy-hook address checks. Pin one or two unique 43-character base64url thumbprints. The parameter allows 532 printable ASCII characters, enough for two 200-character URLs and two thumbprints in compact JSON. The broker fetches the JWKS on the first hook request, accepts only schema-valid keys with a pinned thumbprint, and caches them for five minutes. Fetches refuse redirects, time out after two seconds, and cap the response at 64 KiB. A failed refresh makes the hook unavailable through its existing fixed refusal words. Inline keys are refused. Each trusted JWKS entry must be a bare RSA signing key (kty, n, e, kid, alg "RS256", optional use "sig"); a provider entry carrying other members, such as x5c, or no alg, matches nothing and leaves the hook unavailable.

## What Rovara asks, and when

With an address set, Rovara asks before a task starts ("may this task start?"), on every real approval, Keep and sensitive setting ("may this person decide this, is the sign-in fresh enough, is a second person needed?"; a page that only shows what is needed never asks, and shows the last known requirement or, until there is one, the stricter one: a second person), and offers a company-values reader (`withPolicyHookValues`) for the policy source once one is wired. Each question is signed with the install's own policy-question key (a separate key, not the sign-in or task-token key), which the host passes in (`policyHookInstall`), and an answer counts only when it is signed by a pinned key and names this very question. The service can only make things stricter. When it does not answer, a task start waits and asks again for up to 240 seconds in all (under the server's request timeout), then says "the company rules service did not answer; nothing has started"; an approval is refused at once. Each answer, and each time there was none, is a line in the audit record. The message format is `contracts/shared/policy-hook.v1.json`. With the parameter empty (the default), nothing here runs.
