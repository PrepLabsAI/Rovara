## Before M1.2 runs untrusted candidates

M1.1 qualifies only Rovara's own fixture. These must be done before a candidate repository's code runs on a qualified runner:

- [x] Build-container egress was broader than "registry egress": the default bridge reached the VPC, the host (the worker on `0.0.0.0:8080`), other runs and the internet. Done (H1, 2026-10-19), in code only, not yet deployed:
  - Builds run on their own per-run bridge `rvb<8 hex>` (not `--internal`: package registries need the internet), app and executor on the per-run `--internal` bridge `rvi<8 hex>`. The default bridge is no longer used, and the source copy runs with `--network none`.
  - `packages/worker/ec2/boot.sh` installs the host firewall through the reboot-safe `rovara-container-firewall` unit (the worker unit `Requires=` it): `DOCKER-USER` drops from `rvb+` to `10/8`, `172.16/12`, `192.168/16`, `100.64/10`, `169.254/16` and `127/8`; drops from `rvi+` to anything outside an `rvi` bridge; `INPUT` drops from `rvb+` and `rvi+` (no container reaches a host port); IMDS stays dropped; IPv6 gets `INPUT` drops where `ip6tables` exists (Docker IPv6 is off on the worker, so this is defence in depth). Cross-run traffic between two `rvi` bridges is left to Docker's own isolation chains, and the Linux CI test checks it.
  - DNS: Docker's embedded resolver forwards from the container's network namespace, so the VPC resolver (a private address, exempt from the worker security group) needs an exception. The firewall reads the nameservers in `/etc/resolv.conf` and `/run/systemd/resolve/resolv.conf` and lets `rvb+` reach only those, on port 53. CI cannot reproduce a private resolver (its upstream is public), so this is verified by the contract test and first proven live on the next runner.
  - Two new required probes: `build-lateral-denial-v1` (the build container connects to its gateway at the worker port and to a private address; exit 7 only if both time out) and `app-host-denial-v1` (the app starts behind a guard that connects to the host on its internal bridge at port 8080 and starts only if that times out). The network policy digest moved to `e2e-web-api-network-policy/v2`.
  - **Requalify after deploy.** The required probe set and the network policy digest changed, and a running worker only gets the firewall from the boot script of a new instance. The runner registered on 2026-10-19 (`i-0cfe8d699d3b4b7af`) predates the walls: launch a new qualification runner from the new worker image and register it (`scripts/test-qualify-runtime.ts`) before any candidate code runs. A domain allowlist or a registry-only proxy remains a future option.
- [x] Chromium ran with `--no-sandbox` (Ruling P: the container was the only boundary, so one renderer exploit by a hostile candidate page reached the executor and its result files). Done (H2, 2026-10-19), in code only, not yet deployed:
  - `--no-sandbox` is gone from `launchLocalChromium` and nothing falls back to it: when Chromium's own namespace sandbox cannot start, Chromium exits and the run is unavailable (exit 2). The container walls are unchanged: non-root, `--cap-drop=ALL`, `no-new-privileges`, `--read-only`, internal network. No capability, no `--privileged`, no `seccomp=unconfined`.
  - The executor container, and only it, runs under `packages/verifier/assets/executor-seccomp.json`: Docker's default profile (moby/profiles@6fe7deb1, `seccomp/default.json`) plus four unconditional rules, each marked `rovara:`: `unshare` and `clone` with namespace flags (all but `CLONE_NEWCGROUP`, and `CLONE_NEWTIME` for `unshare`), and `chroot` (Docker only allows it with `CAP_SYS_CHROOT`, which `--cap-drop=ALL` removes). `clone3` stays answered with ENOSYS, `setns`, `mount` and the rest stay denied. The app and build containers keep Docker's default profile, so the candidate's own code cannot create user namespaces.
  - Shipping: the Docker CLI reads a `--security-opt seccomp=<path>` file on the client side, which is the worker container, so the profile ships in the worker image beside the other verifier assets and nothing is added to `boot.sh` (its user-data headroom is untouched). Its digest is pinned in contracts (`E2E_EXECUTOR_SECCOMP_PROFILE_SHA256`); the Docker host refuses to be built over any other bytes, a symbolic link or an oversized file.
  - The executor checks the sandbox on every run that launches a browser: it reads each renderer's `/proc/<pid>/status` and `uid_map` (a seccomp filter beyond the browser's own, its own PID namespace, its own user namespace; needs Linux 5.9+ for `Seccomp_filters`), writes `chromium-sandbox.json`, and exits 2 (`chromium-unsandboxed`, or `chromium-sandbox-unverifiable` when the kernel cannot show it) before any case runs. The smoke check of the executor image does the same.
  - New required probe `chromium-sandbox-v1` (the ninth; a passing web probe on the CSV scenario): its retained evidence carries the attestation, which the registrar re-judges with the same pure evaluator, bound to the probe's run and group. A runner whose Chromium is unsandboxed fails it (the executor refuses to run), and so does one with `user.max_user_namespaces=0`.
  - Hosts: Amazon Linux 2023 needs `user.max_user_namespaces > 0` (the default) and has no AppArmor userns restriction. The Ubuntu 24.04 CI runner restricts unprivileged user namespaces for AppArmor-confined containers, so the `linux-runtime` job runs `sysctl -w kernel.apparmor_restrict_unprivileged_userns=0`; production does not need it. If the sandbox cannot work on a runner, the fallback to discuss is the gVisor runtime, never `--no-sandbox`.
  - **Requalify after deploy.** The required probe set changed again (nine probes), so a runner registered before this is not READY for the new set: launch a new qualification runner from the new worker image (it carries the profile) and register it with `scripts/test-qualify-runtime.ts` before any candidate code runs. This and the H1 requalification are one run.
