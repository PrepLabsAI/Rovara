# Ruling M1.4-AGENT-SEAM: how Rovara drives e2e 0.20.0's agent

Task 4.0. Status: ruled, by reading `e2e@0.20.0` (the vendored `upstream/e2e-0.20.0.tgz`, installed at `node_modules/e2e`), the AI SDK `ai@7.0.127` source (downloaded to read only, not installed), and `@ai-sdk/provider@4.0.21` (installed). No model call and no AWS call was made.

Paths below are relative to `node_modules/e2e/dist` unless they start with `ai:` (the `ai@7.0.127` package, `src/`) or `provider:` (`node_modules/@ai-sdk/provider/dist/index.d.ts`).

## Decisions

| Question | Ruling |
|---|---|
| (a) Request and result shape | The act loop calls `doGenerate` of an AI SDK **v4** language model with `prompt`, `tools`, `toolChoice` and nothing else that matters. It does **not** send `maxOutputTokens` or `temperature` (the plan assumed `maxOutputTokens`). The worker sets both. The result is a `LanguageModelV4GenerateResult`. |
| (b) Pin the toolset, no pixels | **Not possible through config.** Use the fallback: a custom executor built with `createToolLoopExecutor`, whose tools are the closed set `tap, type, press, select, scroll, navigate` (plus the loop's own `complete_step`). The channel schema and the worker refuse any other tool name. `vision` is not an `act` option, so "`vision: false`" in the plan means: no file parts anywhere, enforced by the channel schema. |
| (c) Where actions and stop codes are recorded | Report: one `engine` event per action with redacted prose in `detail` (no node ids). The always-kept ledger comes from our own executor, which holds the observation. `testId` is only in the observation text line, not in the executor's node tree. Stop code: step `status` plus `error.code`. |
| (d) Custom `cache.store` for replay | Mechanically yes (read-only store). **Not from the ledger as specified**: it lacks what a replay needs. Replay should serve e2e's own `ActionTrace`, captured by a write-only store during the verified round. This amends "candidate rounds keep `cache: off`" (accepted as M4-A; Task 4.3 sets the capture store). |

Two further findings that bind later tasks (details in "Findings that need a decision" below): the `ai` package is **not installed** and the loop cannot run without it, and the loop retries in ways the "no retries" rule must account for.

## (a) The exact `doGenerate` options and result

### Who calls `doGenerate`

- `agent.act` dispatches to the agents entry's executor. The built-in one is `createBuiltInAgent` (`agent/default-agent.js:42-93`), which is `createToolLoopExecutor` (`agent/tool-loop.js:79-100`) plus the grammar toolset.
- `runStep` loads `ai` with `import('ai')` (`agent/tool-loop.js:90`, `agent/ai-sdk.js:42-56`) and builds `new ai.ToolLoopAgent({...})` in `buildLoop` (`agent/tool-loop.js:241-262`) with exactly: `model` (the model wrapped in a stall guard), `instructions`, `tools`, `toolChoice`, `providerOptions` (only when the model's provider is OpenAI or Azure Responses, so never for ours), `maxRetries: 5` (`agent/model/sdk.js:30`), `headers` (`internal/client-identity.js`: user-agent, http-referer, x-title), `stopWhen` and `prepareStep`.
- `ToolLoopAgent` goes through `generateText`, which calls `stepModel.doGenerate({ ...stepCallSettings, tools, toolChoice, responseFormat, prompt, providerOptions, abortSignal, headers })` (`ai: src/generate-text/generate-text.ts:1040-1056`). `stepCallSettings` is `maxOutputTokens, temperature, topP, topK, presencePenalty, frequencyPenalty, stopSequences, seed, reasoning` from the agent settings (`ai: src/prompt/prepare-language-model-call-options.ts`). The act loop sets none of them, so all are `undefined`. `responseFormat` is `undefined` (no structured output on the act path). Only the judgment path (`assert`, `waitFor`, `extract`) sets `maxOutputTokens: 8192` and a schema (`agent/invocation.js:20,203`, `agent/model/sdk.js:67-82`). Rovara never calls those, and the channel schema refuses their shape.

### The wrapper in front of our model

`withStallGuard` (`agent/model/stall.js:17-51`) wraps the model with `ai.wrapLanguageModel`, so the model that `ai` sees is a wrapper object. It forwards `{ ...params, abortSignal }` where `abortSignal` is the caller's signal merged with a 120 s stall signal (`stall.js:9`). A stalled request becomes a **retryable** `APICallError`.

### Options that reach our `doGenerate` (LanguageModelV4CallOptions, `provider:1448`)

| Field | What the act loop sends | Channel handling |
|---|---|---|
| `prompt` | `LanguageModelV4Prompt` (`provider:1093`): `system` message (string, from `instructions`; `agent/tool-loop.js:243-246`, `hints.instructions` returns the plain string for a non-Anthropic provider, `agent/model/provider-hints.js:27`), then `user` (text parts), `assistant` (text and `tool-call` parts with parsed `input`), `tool` (`tool-result` parts, `output` of type `text` or `error-text` for our string tools) messages | Subset in `E2EModelChannelCallSchema`. No file, reasoning, custom or approval parts, no `providerOptions`. |
| `tools` | Function tools only (`ai: src/prompt/prepare-tools.ts:52-62`): `{ type: 'function', name, description?, inputSchema (JSON Schema), strict? }`. On the last two turns only `complete_step` is active (`tool-loop.js:496-513`). | Names restricted to `E2E_AGENT_TOOL_NAMES`, unique, `inputSchema` bounded JSON. |
| `toolChoice` | `{type:'required'}` normally, `{type:'auto'}` after a model refuses forced choice (`tool-loop.js:337-361`), `{type:'tool', toolName:'complete_step'}` on the final turns (`tool-loop.js:511`). | Same three, no `none`. |
| `maxOutputTokens`, `temperature`, `topP`, `topK`, penalties, `seed`, `stopSequences`, `reasoning`, `responseFormat` | Not sent (undefined). | `maxOutputTokens` optional, 1 to 1024. The others are refused as unknown keys. The **worker** sets output cap 1024 and temperature 0 from the route. |
| `providerOptions` | Not sent for `provider: "agentx-e2e"` (the hints are keyed on the provider name; `provider-hints.js:49-58`). | Refused. |
| `headers`, `abortSignal` | Sent. | Never put on the wire. The in-executor shim uses `abortSignal` to cancel the socket request; the worker applies its own 30 s timeout. |

### The result we return (`LanguageModelV4GenerateResult`, `provider:727`)

- `content`: `Array<{type:'text', text} | {type:'tool-call', toolCallId, toolName, input: string /* JSON text */}>` (`provider:508,545`). We return only those two kinds. Reasoning, file, source, `tool-result` and provider-executed content are never produced (the response schema refuses them).
- `finishReason`: `{ unified: 'stop'|'length'|'content-filter'|'tool-calls'|'error'|'other', raw: string | undefined }` (`provider:635`).
- `usage`: `{ inputTokens: { total, noCache, cacheRead, cacheWrite }, outputTokens: { total, text, reasoning } }` (`provider:675`). `ai` converts it to the numbers that `trackModelCalls` records (`agent/primitives.js:701-721`).
- `warnings: []` is required. `response`, `request`, `providerMetadata` are optional.
- The model object itself must pass `isModelInstance` (`config/agent.js:257-265`): `specificationVersion`, `provider`, `modelId` strings and a `doGenerate` function. Rovara's frozen wrapper in `packages/verifier/src/application-runtime-bootstrap.ts:288-307` already has `provider: "agentx-e2e"`, `modelId: routeId`, `specificationVersion: "v4"`. `ai`'s `wrapLanguageModel` also reads `model.supportedUrls` (`ai: src/middleware/wrap-language-model.ts:79`); it is only used for file URLs, which never occur, but the wrapper should expose `supportedUrls: {}` (Task 4.3).

### What the channel therefore is

`E2EModelChannelRequestSchema` is `{ schemaVersion, runId, caseId, stepIndex, callIndex, call: { prompt, tools?, toolChoice?, maxOutputTokens? } }`, at most 256 KiB, strict. `E2EModelChannelResponseSchema` carries either the `ok` content (text and tool-call only, `usage` with `outputTokens` at most 1024) or a typed `error` code, at most 32 KiB, with the worker's `receiptId`. Every request the worker receives gets a receipt, including a protocol or busy refusal (`refused-protocol`, `refused-busy`). An `ok` answer finishes with `stop` or `tool-calls` only: a `length`, `error`, `content-filter` or `other` finish is returned as an `invalid-output` or `provider-error` error, so a truncated tool call never looks like success. The `callIndex` in the request is advisory; the worker assigns the receipt's `callIndex` from its own per-step counter (0, 1, 2, ...), takes `runId`, `caseId` and `stepIndex` from the run's own position, and refuses a request whose values differ.

## (b) Pinning the toolset, pixel tools and `vision`

### Why config cannot do it

- The built-in toolset is derived, not configured. `createGrammarTools` (`agent/primitives.js:221-459`) offers one tool per verb in `context.target.verbs`, which comes from the **engine's declaration** (`engine/session.js:156-195`, `declaredVerbs`), not from agent config. The agents entry takes `system` and `tools`, and both only **add** (`default-agent.js:51-54`; `docs/reference/config.mdx`, "agents").
- The `screenshot` tool and the five point tools (`tap_at`, `hover_at`, `type_at`, `press_at`, `select_at`) are offered whenever `!context.pixelsTainted` (`agent/primitives.js:439-446`), and `pixelsTainted` is true only after a secret fill in the attempt (`run/secrecy.js:23-24`). That is incidental protection and we cannot rely on it: a session restored from cookies, or an agent step that runs before any `Secret` fill, still gets the pixel tools.
- The built-in prompt takes a screenshot on its own when the page lists no interactive node (`default-agent.js:56-65`).
- `vision` is **not an `act` option.** `act` throws `UNSUPPORTED_CAPABILITY` for `vision` and `schema` (`docs/reference/agent.mdx`, end of "agent.act"); `vision` belongs to `assert`, `waitFor` and `extract`, and to custom executors only as `vision?: true` for `assert` (`agent/executor.d.ts:485-486`). So the plan's "`vision: false`" cannot be passed to `act`. The equivalent guarantee is: no tool that attaches pixels, a prompt that never carries a file part, and a channel that refuses file parts (tested in `tests/contract/e2e-model-channel.test.ts`).
- Wrapping the engine to hide verbs would not remove `screenshot`, and it would change what Rovara's own deterministic steps can do.

### Choice: custom executor

Use `createToolLoopExecutor` from `e2e/agent` (public export, `agent/public.js`) as the fallback the plan named. `createGrammarTools` is **not** a public export (`agent/public.js` exports only `createToolLoopExecutor`, `defineTool`, `getToolContext`, `AgentError`, `isAgentError`, and the package `exports` map admits no deep import), so the executor defines its own six tools over `ctx.actions`, as `docs/executors.mdx` shows:

- `tap({target})` calls `ctx.actions.tap({id})`; `type({target, value})` calls `ctx.actions.type`; `press({target, key})` calls `ctx.actions.press`; `select({target, value})` calls `ctx.actions.select`; `scroll({direction, target?})` calls `ctx.actions.scroll`; `navigate({url})` calls `ctx.actions.navigate` (e2e already refuses non-http schemes, and the run network is internal).
- Each tool returns the new observation text (`ctx.observe().text`), bounded; each runs inside the loop's `guard`.
- The prompt (`buildPrompt`) is the goal plus a **tree-only** observation. It never calls `observe({ pixels: true })`.
- No `type_secret`, no `upload`, no project tools, no `observe`, no `back`.
- `maxSteps = maxActions` and `maxModelCalls = maxActions + 4` are set on the agents entry (limits 1 to 100, `config/agent.js:100-101`) and may be lowered per call through `ActOptions`; `maxInputTokens: 32000` is set on the entry (`docs/reference/config.mdx`, "AgentOptions"). The loop's `maxTurns` is `budgets.maxModelCalls` (`tool-loop.js:153`), and the wind-down and forced-verdict turns come from the loop unchanged (`tool-loop.js:28,40,496`).
- Defence in depth: the worker proxy validates every request with the closed schema, so even a bug in the executor cannot show the model a screenshot tool or a file part.

The cost: Rovara owns the system prompt, the tool descriptions and the screen text, which the built-in agent tunes (`ScreenPresenter` diffing, `compactScreenHistory`) and which are not public. Start with full `ctx.observe().text` after each action. If the 32000-token input bound bites on large pages, `prepareMessages` can elide superseded screens. That is a Task 4.3 measure, not a reason to take the built-in agent.

## (c) Where actions and stop codes are recorded

### In the e2e report (`run/steps.d.ts`)

- **Actions:** each committed action is one `StepRecord.events[]` entry with `kind: 'engine'`, `name: <action>` and `detail` = `describeAction(...).summary` (`agent/action-dispatcher.js:489-494`, `agent/actions.js:112-190`; `run/steps.d.ts:19-57` `StepEvent`). The prose is redacted and at most 300 characters, for example `tap button "Download orders"`, `type "orders.csv" into textbox "File name"`, `navigate to "/orders"`. **It has no node id and no separate testId field** (`targetLabel` falls back to the test id only when there is no name, text or placeholder).
- **Counts:** `StepRecord.metrics` has `modelCalls` and `actionSteps` (`run/steps.d.ts:59`); the broker cross-checks `actionSteps` against the ledger's action count, and `modelCalls` against the receipts by the relation under "Report calls against receipts" below.
- **Model use:** `StepRecord.model` has `provider`, `model`, `calls`, `inputTokens`, `outputTokens` (`run/steps.d.ts:74`).
- **Last turns:** `StepRecord.turns[]` keeps at most 12 turns, each with `calls` such as `tap({"target":"n19"})` clipped to 200 characters (`tool-loop.js:50-52`). This is the only place node ids appear in the report, and it is clipped. Do not build the ledger from it.
- **Stop code:** `StepRecord.status` (`passed | failed | blocked | timed-out | cancelled`) and `StepRecord.error.code` (an `AgentErrorCode`). Runtime stops are `STEP_BUDGET_EXHAUSTED`, `STEP_TIMEOUT`, `CANCELLED`, `STEP_NO_CONCLUSION`, `CONTEXT_OVERFLOW`, `MODEL_PROVIDER_FAILED`, `MODEL_OUTPUT_INVALID` (`docs/reference/agent.mdx`). `E2E_AGENT_STOP_CODES` in the contract is exactly that closed list.
- **Cache write:** `StepRecord.cache.write` and `StepRecord.cache.entry` say what happened to the recording (relevant to (d)).

### The ledger (the always-kept record)

The ledger is written by **our executor**, not parsed from the report, because only the executor knows the node it chose and the observation it chose it from:

- `node.role` and `node.name` come from `ExecutorNode` in `ctx.observe({ tree: true }).tree` (`agent/executor.d.ts:93-111`).
- **`testId` is not in `ExecutorNode`**: `projectTree` drops it (`agent/observation.js:297-315`). It is present in the observation `text`, one line per node as `#id role "name" ... testid="..."` (`agent/observation.js:347-348`). The executor extracts it from the line of the target id and records `null` when absent. The line is built from the same redacted observation the model saw.
- `snapshotSha256` is the SHA-256 of that observation text. `valueDigest` is a keyed digest (`e2eAgentValueDigest`, HMAC-SHA256 under a per-run key that the broker generates, hands to the executor for the run and keeps; it is never stored with the ledger) of the typed value, key, option label or scroll direction. `valueLiteral` is kept only when the value is text of the approved goal. `node.name` is the first 120 characters of the name. The `navigate` tool turns an absolute same-origin URL into its app-relative path, drops the query and fragment (which can carry tokens), and records `policy-denied` for any other origin; the ledger schema accepts app-relative paths only. Each step also carries `verdict`: `concluded` (`agent.act` resolved), `failed` (it threw; the stop code says which) or `cut-short` (the ledger was written but the step never reported an end, such as a crash or deadline). The ledger is read only through `parseVerifiedE2EAgentActionLedger`, which requires the ledger's `runId` and `caseId` to be the expected ones and its `valueKeyId` to be the id of the run's value key (a ledger from another run or key is refused; a typed digest with no literal is bound to the key here and checked against the trace later), the ledger's step indexes to equal the approved goals' keys exactly, checks each goal digest, each literal and its keyed digest, and returns a branded, frozen `VerifiedE2EAgentActionLedger`. The plain schema's output is not assignable to that type, and Tasks 4.4 and 4.6 must require it.
- `outcome` comes from the tool result (`ok`) or the failure lead (`action-failed`), or `policy-denied` for a `POLICY_DENIED` error.
- `stopCode` is the step's `error.code` (null when the loop concluded). `receiptIds` are the worker receipt ids the shim got back from the channel; the broker still re-derives them from the worker's own receipt store.

## (d) Can a custom `cache.store` serve replay from Rovara's ledger, read-only?

**The mechanism exists.** `CacheConfig.store` (`types.d.ts:1038`) replaces the file store with any `CacheStore` (`cache/store.d.ts:31-47`): `writable`, `read(keyHash)`, `write(keyHash, ActionTrace)`, optional `delete`. A store with `writable: false` and a `write` that returns `undefined` is read-only. With `mode: 'read-only'` the runner replays hits and writes nothing (`cache/context.js:124-150`). Replay is eligible on the first attempt only (`cache/context.js:148`), which matches `retries: 0`. A custom store is exempt from the CI read-only default (`docs/cache.mdx`, "Modes").

**It cannot be fed from the ledger as specified.** A cache entry is a `TraceEntry { schemaVersion: 'trace-1', createdAt, payload: ActionTrace }` (`cache/trace.d.ts:277-360`). `ActionTrace.actions` needs a `TraceTargetDescriptor` per action (`role, name, text, testId, placeholder, selector, inputPurpose, within, position`), verbatim typed `value`s, press keys, scroll directions and counts, plus `startPath`, `endPath`, `endAnchors` and `goneAnchors`. The replay's end check requires at least one recorded change (`docs/cache.mdx`, "How the end check reads the screen"). Our ledger has role, name, testId and digests only: no end route or anchors (so every replay would end in `end-mismatch` and hand over to a model that is not mounted), and typed values are digests, which cannot be typed again. Adding those fields to the ledger would break its "digests, not values" rule.

**Ruling (recommended, for Task 4.6 and a change to Task 4.3):** serve e2e's own `ActionTrace`, captured during the verified round, and keep the ledger as the redacted audit view.

1. In candidate rounds that contain an `agent` step (ruling M4-A), set `cache: { mode: 'read-write', store: captureStore }` instead of `cache: 'off'`. `captureStore.read` always returns `{status:'miss'}` (so a candidate round never replays: the model always navigates), `write` keeps the `ActionTrace`, and `delete` is a no-op. The runner only writes after a **later deterministic verification step passed** in the attempt (`cache/context.js` `settleStagedTraces`, `docs/cache.mdx` "When a recording is written"), which is the "verified round" condition we want. A failing or unverified round writes nothing.
2. The trace is reviewed with `reviewCapturedE2EAgentTrace` before anything is kept. It must match the verified ledger step one action at a time (e2e records only committed actions, so the trace is the ledger's `ok` actions in order, with the same kind, the same target role, name and test id, and the same keyed digest of the typed value, key, option or direction; a navigation matches by path). A mismatch, a malformed or oversized trace, or a **credential-scan hit** (the trace carries screen text in its target descriptors and end anchors, and typed values verbatim) discards the trace. A discard only loses the replay input: it never fails or changes the round. A kept trace yields a binding `{ runId, caseId, stepIndex, traceSha256, ledgerSha256, actionCount }` that goes into the round's PASS evidence manifest. Replay may use only a trace whose digest is in the manifest of a round whose Rovara verdict is PASS (e2e's own "verified" is only that a later deterministic step passed). A round that is UNKNOWN or FAILED produces no usable trace.
3. The executor hands the captured trace (at most `MAX_CACHE_WIRE_BYTES` = 1 MiB, `cache/store.d.ts:18`) to the worker as operator-only evidence, after the same credential scan as transcripts. Typed values are stored verbatim in a trace (`docs/cache.mdx`, "What a recording holds"), so it is as sensitive as a transcript and never appears on the task page.
4. The replay round (Task 4.6) mounts **no model channel**, runs with `cache: { mode: 'read-only', store: replayStore }`, an agents entry with an executor that has no model (the agent fixture is built lazily, so a model-less custom executor does not fail with `MODEL_UNAVAILABLE` until a step actually needs one: `run/fixtures.js:81-95`), and the same project id, test id, target, agent name and context, app identity and instruction, because the `keyHash` is derived from them (`cache/identity.js`, `cache/trace.js:101-110` `KEY_CONTEXT_FIELDS`). `replayStore.read(keyHash)` returns the stored entry for that hash. `step.cache.mode` of `self-finalized` means reproduced without a model. Anything else is `reproduced: false` with the e2e reason, informational only.
5. A step whose typed value was read off the screen is recorded as a gap (`agent/action-dispatcher.js:496-519`, `docs/cache.mdx` "Limits and gaps") and replay hands off to a model, which is absent: `reproduced: false`. That is the correct, honest outcome.

The controller accepted this amendment (M4-A). The alternative that was offered was a Rovara replay executor that walks the ledger and calls `ctx.actions` after finding each node by role, name and testId. It can only replay `tap` and the values that are text of the goal. It cannot replay a model-chosen typed value. It is weaker, but needs no change to the candidate-round cache setting.

## Findings that need a decision

1. **`ai` is not installed.** `createToolLoopExecutor` and the built-in agent both `import('ai')` at run time (`agent/ai-sdk.js:49`, optional peer `ai ^7.0.0` in `e2e/package.json`). `node_modules/ai` is absent and `package-lock.json` has only `@ai-sdk/provider@4.0.21`. The `ai` module must sit where e2e resolves it from (next to `node_modules/e2e`, in the same tree that qualification installs). Recommendation: pin `ai@7.0.127` (published 2026-10-01, so older than two weeks; its `@ai-sdk/provider` dependency is exactly `4.0.21`, the version e2e 0.20.0 pins, so there is no second copy; other dependencies `@ai-sdk/gateway@4.0.103` and `@ai-sdk/provider-utils@5.0.53`; Node >=22). Later 7.0.x versions depend on `@ai-sdk/provider@4.0.31`, which would add a duplicate. This is a new dependency beyond what D1 allowed (`@aws-sdk/client-bedrock-runtime`). `package-lock.json` is a one-task-at-a-time file; whichever task takes the lock (4.1 for the SDK, 4.3 or 4.5 for the runtime install) must also add `ai`, and the owner should confirm it.
2. **Hidden retries.** The loop and `ai` can send more provider requests than there are agent turns. (i) `ai` retries a thrown `APICallError` with `isRetryable === true` up to `maxRetries: 5` (`ai: src/util/retry-with-exponential-backoff.ts:80-88`), and the stall guard raises exactly that error after 120 s. (ii) The loop re-sends after a context overflow once (`tool-loop.js:377-401`), after a forced-tool-call mismatch (`correctForcedTurn`), after a rejected forced `tool_choice` (`freeToolChoiceRetry`, `tool-loop.js:337-361`), and after a text-only reply (`continueAfterTextReply`, `tool-loop.js:269`). The "no retries" rule therefore needs three things from Tasks 4.1 and 4.3: the shim's `doGenerate` throws a **non-retryable** error for every channel failure (a plain `Error` or an `APICallError` with `isRetryable: false`), so `ai` never re-sends; the worker counts **every request it receives** against `maxModelCalls` and the group cap, whatever the loop meant it as, which is what the `+4` headroom is for; and a refusal or error response is never worded like a `tool_choice` rejection. The worker enforces the 30 s per-call timeout, so the 120 s stall guard never fires first.
3. **`maxOutputTokens` is not sent**, so the worker sets 1024 (and temperature 0) on the provider call itself. The channel accepts `maxOutputTokens` only up to 1024 for forward compatibility.
4. **A model that calls an unknown tool name** is refused at the response schema (fail closed, `invalid-output`), so the next prompt can never carry a hallucinated tool name. A request carrying one is refused as `channel-protocol`.
5. **An agent verdict is not a case verdict.** `agent.act` resolves on a `passed` verdict and throws `AgentError` on `failed` or `blocked` (`docs/reference/agent.mdx`). The driver must catch it, record the stop code and receipts, and map any `AgentError` to UNKNOWN (D3 applies only to a deterministic assertion mismatch after a step that completed). A `passed` verdict with zero committed actions can never satisfy a scenario: Task 4.4 requires at least one `ok` ledger action and still requires the deterministic assertions.

## Report calls against receipts

The worker counts every request it receives (ruling M4-C), but e2e's report counts a model call only when a turn ends (`agent/primitives.js:707-721`), so a request that errored, was refused or was re-sent has a receipt and no report call. The relation, implemented by `checkE2EStepModelAccounting` and `checkE2EGroupModelBudget`:

- Every call in the report (`metrics.modelCalls`) has exactly one `ok` receipt: `okReceipts === metrics.modelCalls`.
- Every other receipt has a non-`ok` outcome (provider error, timeout, budget, refusal, invalid output). It is allowed, and it counts.
- All receipts, whatever their outcome, count toward the step budget (`maxActions + 4`) and the group caps (calls, input tokens, agent steps).
- Per-step indexes are `0..n-1` with no gap or duplicate and non-decreasing start times; every receipt belongs to this run, case, step and route revision.
- A receipt of the `rovara-scripted` provider is accepted only in a qualification round. The scripted route (`rovara-scripted/...`) exists only with `scope: "qualification"`.

The checker clamps the step limit to 8+4 (and the group limits to their caps) whatever the caller passes; a bad number counts as 0. Receipts the worker refused for budget (outcome `budget`) are the worker enforcing the limit, so they surface as `budget-refused` (Task 4.4 maps it to `model-route-budget-exhausted`); more than the limit of other receipts is `over-step-budget`. Receipts are also compared to the route's provider and model, and a repeated receipt id fails. The ledger is tied to the worker's receipts by `crossCheckE2EAgentLedgerReceipts`: every ledger receipt id must be a worker receipt of the ledger's run, case and step, and no id may repeat. The receipt and ledger schema bounds are ceilings from the D2 caps. A pinned route may lower any of them, so Tasks 4.1 and 4.4 also check against the route definition they hold. The route pins the Bedrock `region`, and `e2eModelRouteInvokedIdentifier` says which identifier is invoked: the inference profile ARN when set (same region; a system profile must be the profile of `modelId`), else the model id. The D1 model is `us.anthropic.claude-haiku-5-5` (ruling M4-K).

## Ruling M4-Q (Task 4.1): one provider for the e2e agent, through model-runtime and pi-ai

Owner, 2026-10-21: "what if the customer doesn't want to use AWS Bedrock? We should only use one AI gateway provider for the overall process." This replaces the earlier Task 4.1 addendum (a Bedrock Converse path through `@aws-sdk/client-bedrock-runtime`, Ruling M4-P), which is withdrawn. Evidence: `pi-ai@1.3.0` (`dist/api/*`, `dist/providers/data/*`), the bundled Claude API model reference, and the loopback tests in `tests/unit/e2e-provider-invoke.test.ts` and `tests/unit/e2e-agent-model-seam.test.ts`.

### What it is

- **The provider is the installation's worker provider** (`worker-model-provider`, seen by the worker as `AGENTX_MODEL_PROVIDER`; owner item O1): Bedrock through the worker role, or Anthropic, OpenAI or OpenRouter through the provider key's Secrets Manager ARN, the same ARN the coding agent's default uses. It is never a ChatGPT plan and never the project's model selection.
- **The model is a separate small-model choice per provider**, `DEFAULT_E2E_AGENT_MODELS` in `config.ts` (not a `ModelRole`: a role's default can fall back to Bedrock, and e2e never falls back): Bedrock `us.anthropic.claude-haiku-5-5`, Anthropic `claude-haiku-5-5`, OpenRouter `anthropic/claude-haiku-5.5`, OpenAI `gpt-5.4-mini`. The pinned pi version's catalog has all of them (1.3.0 has Haiku 5.5 for Bedrock, Anthropic and OpenRouter), so no catalog overlay is kept; `tests/unit/e2e-provider-config.test.ts` fails if a pi change drops any of them. **The OpenRouter id is provisional and its route stays unapproved until a canary on an OpenRouter installation records the model OpenRouter reports serving it (owner item O5).**
- **`createE2EProviderInvoke(definition, { environment, readSecret, fetch })`** (`e2e-provider-invoke.ts`) is the `invoke` the governed route takes. It calls pi-ai's API adapters (`anthropic-messages`, `openai-responses`, `openai-completions`, `bedrock-converse-stream`) directly, as coding's `safeProviderStream` does, and never `ModelRuntime.create()` (whose auth resolution reads the ambient environment and credential stores) or `createModelRuntimeWithFallback`. A missing provider secret, or a model the catalog lacks, makes every call `provider-error` and the case UNKNOWN; there is no fall back to Bedrock. `@aws-sdk/client-bedrock-runtime` is not a model-runtime dependency (pi-ai brings its own).
- Options on every call: the route's controller as `signal`, `maxRetries: 0`, `cacheRetention: "none"` (no cache points, no cache-write premium), `maxTokens` from the route, an explicit key (or Bedrock region), the base URL from `TRANSPORTS` (shared with coding in `transport.ts`), an observing `fetch`, and no temperature.

### Haiku 5.5 forces three contract changes

1. It rejects `temperature: 0` with a 400 (it accepts only 1 or none), so the route definition has `sampling: "provider-default"` and no `temperature`. Sampling is the provider's default (owner item O2); a flaky navigation stays UNKNOWN, never PASS.
2. It thinks by default (adaptive, medium effort), and thinking counts against the 1024-token output cap while its thinking blocks would have to be passed back, which the channel schema refuses. The final payload carries thinking `disabled` and effort `low` (`thinking: "off"`, `effort: "low" | null` in the definition). On Bedrock that is `additionalModelRequestFields` (the canary confirms Bedrock accepts `output_config`; if not, drop the effort and keep thinking disabled). OpenAI gets `reasoning.effort: "low"` (the amendment said `minimal`; pi's own mapping turns `minimal` into `low` for GPT models and recent GPT-5 models reject `minimal`; unverified live). OpenRouter gets `reasoning: { effort: "none" }` for Anthropic models (provisional).
3. Forced tool choice is accepted by Haiku 5.5; Opus 5.5 and Sonnet 5.5 would 400 on it, so a future change of model must be reviewed.

The definition is `{ routeId, revision, scope, provider, modelId, region, inferenceProfileArn, secretArn, openRouter, budgets, promptProtocol, sampling, thinking, effort, vision }` (`E2E_MODEL_PROVIDERS = [...MODEL_PROVIDERS, "rovara-scripted"]`); a Bedrock route has a region and no secret, a keyed route has a secret ARN and no region, OpenRouter alone carries its routing policy, the scripted route carries none. The receipt gains `servedModelId` and `servedUpstream` (both nullable); `provider` and `modelId` keep meaning the route's, never the served model's. Every route digest changes, and none had been approved, so nothing migrates.

### The Step 0 proofs

- **(a) The real e2e loop round-trips through the pi-ai invoke for every provider.** `createToolLoopExecutor` from e2e 0.20.0, with `ai@7.0.127` and the channel adapter, runs two turns (a `tap`, then `complete_step`) against a loopback Bedrock endpoint (HTTP/2, AWS event-stream frames) and against a fake `fetch` for Anthropic, OpenAI and OpenRouter. One request per turn, the tool executes, the verdict is `passed`, the global `fetch` is never called, and the receipts name the pinned model.
- **(b) A Bedrock HTTP error stops after one attempt (a 429 and a 500 each reach the endpoint once); a connection-level failure may be retried inside one receipt.** pi-ai 1.3.0 builds its Bedrock client with no `maxAttempts` (checked in every pi version from 1.0 to 1.3), so the AWS SDK retries a throttle or a 5xx twice more; reproduced against the loopback endpoint as three requests. The amendment proposed aborting the call's controller from `onResponse`, which **hangs** the SDK's retry loop (it never settles, even with a caller deadline). The mechanism that works is to **throw** a plain error from `onResponse` on any status of 400 or more: `onResponse` runs inside the retry loop at the deserialize step and sees every attempt, and the loop classifies an error with no retry trait as a client error and stops. The caller gets an error carrying the status (429), never the provider's text. Owner item O3 (setting `AWS_MAX_ATTEMPTS=1` process-wide) is not needed for HTTP errors. **A connection dropped before any response is different:** `onResponse` never runs when there is no response, and the SDK's standard strategy retries a network error, so the loopback saw 3 requests for one receipt. The owner accepted this (O3, 2026-10-21, Ruling M4-V): hidden connection-level retries stay inside one receipt and the 30 s call bound, and the reserved input bound is charged whenever no HTTP status was seen (and whenever a 2xx response was accepted, even one cut before its first delta), since each attempt may have been processed. The keyed adapters make no retry at `maxRetries: 0`; the tests assert exactly one `fetch` per call for a 429, a 500 and a dropped connection. The environment guard still refuses `AWS_MAX_ATTEMPTS` other than 1.

### The environment guard

pi-ai's clients read the process environment, and the worker cannot scrub its own without changing the coding agent. `startE2EModelProxy` therefore **refuses to start** (RUNTIME_UNAVAILABLE "this worker's environment can redirect model calls", naming the variables and never their values) for a route on a real provider when any of these is set and non-empty: `AWS_BEARER_TOKEN_BEDROCK`, `AWS_BEDROCK_SKIP_AUTH`, `AWS_BEDROCK_FORCE_HTTP1`, `AWS_PROFILE`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`, `AWS_ENDPOINT_URL`, `AWS_ENDPOINT_URL_BEDROCK_RUNTIME`, `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY` (any case), `NODE_USE_ENV_PROXY`, `NODE_TLS_REJECT_UNAUTHORIZED`, `NODE_EXTRA_CA_CERTS`, `PI_CACHE_RETENTION`, `AWS_CONFIG_FILE`, `AWS_SHARED_CREDENTIALS_FILE`, `AWS_CONTAINER_CREDENTIALS_FULL_URI`, `AWS_CONTAINER_CREDENTIALS_RELATIVE_URI`, `AWS_WEB_IDENTITY_TOKEN_FILE` (and `AWS_ROLE_ARN` together with it), `AWS_EC2_METADATA_SERVICE_ENDPOINT`, and `AWS_MAX_ATTEMPTS` with any value other than 1. pi-ai and the AWS SDK always read the real process environment, so the guard always checks `process.env` (and the caller's environment as well), at start and again on every provider call. A worker on ECS or another host that supplies credentials through the container or web identity variables cannot run agent steps until the guard is relaxed on purpose. Explicit options pin the rest: the region from the definition, the base URL from `TRANSPORTS`, and the key from Secrets Manager. **For Bedrock the base URL does not pin the endpoint.** The route names `https://bedrock-runtime.<region>.amazonaws.com`, but pi-ai takes its explicit-endpoint path (`config.endpoint`) only when no region is configured anywhere, and a worker has `AWS_REGION`; passing no region would let that variable choose the region, which is worse. So with the route's region the SDK resolves the same standard regional endpoint itself, and the environment guard closes the overrides that could change it. Not covered, and carried to operations and 4.3: an `endpoint_url` or `max_attempts` inside a shared config file at its default path (`~/.aws/config`); the guard refuses only the variables that relocate that file. A worker behind a corporate proxy cannot run agent steps until proxy support is added; it fails closed with that reason. The scripted route, which calls no provider, is not subject to the guard.

### The route must be the installation's

The worker refuses a route whose provider or secret differs from its own settings: the installation's provider is `AGENTX_MODEL_PROVIDER` (unset is Bedrock, as for the coding agent) and a keyed provider's secret is that provider's worker secret-ARN setting (`AGENTX_<PROVIDER>_SECRET_ARN`). The proxy refuses to start, and every call of an invoke built for another route fails, with `model-route-changed-reapprove`, so a stale or forged definition cannot reach a provider the owner did not choose. The scripted route is exempt.

### Test overrides

The loopback Bedrock endpoint and the provider-scoped environment (for example skipping auth for a fake endpoint) exist only on `createE2EProviderInvokeForTesting` in a separate module. It is not in the package index or its exports map, `createE2EProviderInvoke` takes no such argument and ignores one passed through a cast, and a test asserts that nothing but tests imports the testing module.

### The request, the answer and the accounting

- **Final payload.** The last `onPayload` hook removes `temperature`, `top_p` and `top_k`, sets the thinking and effort fields above, applies OpenRouter's routing policy from the definition (`allow_fallbacks: false`, `require_parameters: true`, `data_collection: deny`, the allowlist) and removes `models` and `route`, and asserts that the payload's model is the pinned identifier and that its tools are exactly the offered ones. The proxy then scans the final payload for credentials (values, keys and credential shapes, including the provider key the invoke holds), and a hit stops the call before it is sent (`refused-credential-match`). The digest of the payload as sent is kept with the transcript (`providerPayloadSha256`).
- **Tool choice.** `auto | required | tool` maps to Bedrock and Anthropic `auto | any | {tool}`, OpenAI `auto | required | {function}` and OpenRouter `auto | required | {function:{name}}`. OpenAI's Responses ids are `call_id|item_id`; the bar is carried as a dot on the channel (the channel id grammar has no bar).
- **Served model.** A keyed provider must say which model answered (the stream's model, observed without reading bodies; OpenRouter also reports its upstream). It must be the pin or the pin with a date suffix (`-YYYY-MM-DD`, `-YYYYMMDD`), otherwise `invalid-output`; the receipt carries it, and `checkE2EStepModelAccounting` re-checks it (`receipt-served-model-mismatch`). **Bedrock reports none, as Converse never did**, so its pin is held by what is invoked; the collector-side check (`checkE2EStepModelAccounting`) allows an ok receipt with no served model only for `amazon-bedrock` and `rovara-scripted` (the identifier comes only from the definition; no request field can name a model). OpenRouter may echo a canonical slug that differs from the requested id; the canary must record it and an explicit alias list per model follows if it differs.
- **Usage.** Charged input is `input + cacheRead + cacheWrite`. pi always returns a usage object, so a stream whose input is zero is treated as missing usage: `invalid-output`, the reserved bound charged, the transcript noted. A failure after output started is `provider-error` with the reserved bound charged, because the call may have been billed. pi's stop reasons map `stop` to `stop`, `toolUse` to `tool-calls`, `length` to `length`, and anything else (including a Haiku 5.5 safety refusal) to an error, so a refusal is UNKNOWN with no fallback.
- **Token bounds.** Before every call the route refuses a prompt whose true upper bound (its size in bytes plus 1024 for the provider's own overhead) could pass the per-call input limit, and the group and the day reserve that bound, so no call in flight can pass a cap. This makes the effective prompt about `maxInputTokens - 1024` bytes (about 31 KB at 32000) until a token counter is wired in; Haiku 5.5's tokenizer counts about 30 percent more tokens for the same text, so the token caps bind sooner, which is safe. A provider count above the bound is charged in full (the receipt holds at most 64000) and flagged `overrun` in the proxy summary.

### Limits and what is carried

- **The pin and IAM.** The pin is held in code. Verifying that the worker role can invoke the pinned identifier (Bedrock) or read the provider secret (keyed) belongs to the Task 4.8 check, not to IAM changes by 4.2 or 4.9: the shared worker role also serves coding on `foundation-model/*`. A scoped STS session policy for the e2e client is optional defence in depth (4.3) and needs owner approval.
- **Credential scan limits (defence in depth; e2e masks secure fields and the agent never receives a password).** The scan does not catch a password split across two text parts, a case-changed copy (an accessible name after `text-transform` styling), or an HTML-entity-encoded or unaligned-base64 copy. It matches the email case-insensitively and the password exactly. A short or common-word local part (for example `test`) over-redacts and over-refuses; the seeded-account generator should use high-entropy local parts (carried to 4.3 and 4.7).
- **Carried to Task 4.3:** `beginStep`/`endStep`, `addCredentialValues` for cookies reported during the run, a 0700 socket directory and `socketOwner`, the prompt shapes the scripted double reads (or `goalCandidates`), a throwing `globalThis.AI_SDK_DEFAULT_PROVIDER` in the executor (`@ai-sdk/gateway` is installed with `ai`), and a check that worker sources never import `@agentx/verifier/executor`. **Carried to Task 4.2:** the broker-backed `E2EDayBudget` (with `reserve` and `settle` failures handled, as the route does). **Carried to Task 4.8:** the provider-aware check.
- **The gateway.** e2e has no implicit default model; `gateway` appears only in the example text of two error messages in `config/agent.js`. `tests/unit/e2e-agent-model-seam.test.ts` asserts that no e2e runtime source calls it, that a string model is refused, that no model resolves to none with `MODEL_UNAVAILABLE` and no `fetch`, and that the Rovara adapter resolves to provider `agentx-e2e`.
