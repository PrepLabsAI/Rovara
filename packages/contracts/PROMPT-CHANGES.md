# Static prompt changes (TE-F4)

This additive M2 / 0.5.19 contract detects changes in supplied source text. It has no production callers yet. TE-F3 and TE-F10 should read `PromptChangeReportSchema`, `detectPromptChanges`, `detectPromptChangesInDiff`, `promptChangesNeedEval` and `promptChangesNeedSideBySide`, exported from the contracts barrel.

```ts
const { report } = detectPromptChanges({
  files: [{ path: "prompts/summary.prompt", before: baseText, after: headText, wholeFile: true }],
});
const decision = promptChangesNeedEval(report); // { needed, reason }
```

`detectPromptChangesInDiff(diffText)` reads Git/workspace unified diffs, including quoted/octal filenames, both rename names, new/deleted/binary files, newline markers and LF or CRLF line endings (a lone CR remains hunk content; CR-only framing is unsupported). Each hunk retains its own boundaries and line offsets. The whole-file entry point ignores caller-supplied hunk metadata, so it cannot bypass side caps; overflowing parsed line offsets are refused. It cannot supply whole-file coverage, even for an added file. Whole-file callers must explicitly pass `wholeFile: true`; missing before/after text needs the corresponding `added`/`removed` status. Hunkless prompt renames carry null content fingerprints rather than invented empty-file hashes.

The result is `{ report, stats? }`. Opt in with `{ stats: true }`; stats contain only numeric work/byte/file counts and are outside the strict report schema. Serialize only `report` into evidence. `none_found` requires complete coverage. Unreadable or capped input is `incomplete`, including when some changes were found. The one exception is a truncated item list: its status remains `changes` as required by v1, and its coverage still records any incompleteness. Both selectors conservatively return `{ needed: true, reason: "incomplete" }` for incomplete coverage. The side-by-side selector uses full counts, including changes beyond the first 500 items.

The report contains no prompt, system instruction, tool schema, endpoint or diagnostic text. Values are unsalted SHA-256 fingerprints. Short or predictable values can be guessed by hashing candidates; this is by design under the brief, not encryption or a secrecy guarantee against guessing. The explicit Q1 exception permits bounded ordinary repository paths in `path`/`oldPath` only; they are metadata. The path allow-list is letters/numbers, spaces, underscore, dot, slash and hyphen, with a non-space first character, no leading `---`, and at most 512 UTF-16 units. Hidden, control, bidi and variation-selector characters and markup are refused to `path_refused`; `pathFingerprint` and `oldPathFingerprint` reference refused names. Paths over 4096 UTF-8 bytes are refused before path rules, make coverage partial, and hash a domain tag, the first 4096 UTF-16 units and the original UTF-16 length. Equal-length paths sharing that prefix can share a reference. Only a bounded 128-unit suffix supplies optional extension hints; missing folder context cannot certify completeness. Consumers still render paths through their inert-text function. Valid model names use F0a's **MODEL_NAME_PATTERN**, not its broader echo pattern. Only finite numeric settings and the schema's fixed `SETTING_ENUM_WORDS` may otherwise be echoed. The strict discriminated union does not admit before/after fields on other kinds. Errors and refusals use fixed codes and sentences.

The rules are in `src/prompt-change-rules.ts`:

- Prompt extensions: `.prompt`, `.prompty`, `.dotprompt`, `.jinja`, `.jinja2`, `.j2`, `.hbs`, `.handlebars`, `.mustache`; `*.prompt.md`; `.txt` names containing `prompt` or `system`; and `.md/.txt/.yaml/.yml/.json/.toml` below `prompt`, `prompts` or `system-prompts` folders. Prompt files are fingerprinted as a whole and not scanned a second time as code.
- Code: JS/TS (`js/jsx/ts/tsx/mjs/cjs/mts/cts`) and Python (`py/pyi`), with single/double/triple strings, raw/f strings, templates, balanced interpolation holes, escapes and continuations. It recognizes the brief's literal prompt/system/content, positional generation/template, model-helper, setting and tool-schema patterns. Prompt constants and object/dict keys match whole underscore or camelCase name parts (`system`, `prompt`, `instruction(s)`, `template`) in AI-signal files, including simple TS/Python type annotations. Names ending in DIR, PATH, STATUS, TIMEOUT, ROOT, FILE or URL are excluded. Nonliteral named values (including concatenation and Python parenthesised implicit concatenation) produce `nonliteral_prompt`. Anthropic system text blocks and nested messages/content text under SDK calls are recognized without a separate file-level AI signal. LangChain message-tuple variables also produce `nonliteral_prompt`. Nonliteral SDK prompt/system/messages arguments (variables, concatenations, calls, shorthand and unresolved array entries) mark coverage partial with `nonliteral_prompt`; semantic variable resolution is not attempted and no code is executed. Model/template keys, settings and content/input need an SDK import/require, recognized model prefix or an AI folder (`prompts/models/llm/ai/agents`); input additionally needs a known SDK-call context. A content field needs a role in the same object; system roles retain their kind independent of key order.
- Config: JSON/YAML/YML/TOML/env/INI token or line scanning, including YAML block scalars. No YAML parser, alias/merge expansion or untrusted JSON object construction. Model/setting aliases and enum words are explicit lists, not fuzzy matching; config model keys are case-insensitive. YAML aliases/merges, malformed strings/containers, unsupported executable formats and excessive nesting yield `unreadable_diff`, the fixed v1 reason for unreadable source as well as diff syntax. Ordinary `.txt/.rst/.adoc/.csv/.svg/.css` files outside prompt rules are not executable-source inputs. Embedded `.html/.md/.mdx` text containing an import line, a known SDK package name (the ordinary word `ai` alone is excluded), or a member call of the form `client.sdkMethod(` is conservatively partial; inline scripts are not parsed as a complete program. JS `#private` fields and regex literals containing quotes can produce `unreadable_diff` because this is a lexical scanner, not a full JS parser. Other file types are unsupported and nonempty input fails closed.
- Model prefixes are owned here, all marked **UNVERIFIED** against vendor SDK runs. Unknown names under model keys retain `family: null`. Catalog hosts come from F0a; exact DNS tokens count, suffix lookalikes do not. A host listed under multiple families has a null family hint. Endpoints are never echoed.

Fingerprints remove Unicode format/bidi characters and collapse whitespace, including line wraps. Tool/structured-setting values join lexical tokens, normalizing string content separately so layout around punctuation does not matter. This is deliberately lexical, not a semantic equivalence proof. Interpolation text is balanced and fingerprinted without evaluating or resolving it. Equal fingerprints are matched with queues first, then remaining equal key paths pair by ordinal. IDs hash a domain tag, kind, file hash and line-independent anchor. Rename items use the after path. Hunk offsets affect `line` but not IDs.

Default caps are 2,000 files, 1 MiB per file side, 32 MiB total including path metadata, depth 64, 512 path characters and 500 output items. Options may only lower scan caps. Too many whole-file inputs, duplicate paths or an excessive total refuse the batch rather than choosing an order-dependent prefix. Counts and the digest cover all detected items even when the displayed list is truncated. File-side limits check UTF-8 bytes. Very large strings first fail a cheap UTF-16 lower-bound check. Path mode/AI classification is computed once per file side (shared when not renamed), and inherited token contexts once per token; queues never shift arrays. Scanning is iterative with no input-dependent recursion. Output sorting compares bounded keys; the finite byte/item limits bound comparison work. The work counter charges character passes, tokens, hashing, bounded ancestor visits and sorting comparisons; tests enforce `steps <= 13 * (bytes + 1) + 10000` and `steps(4N) <= 4.5 * steps(N)` for every timing corpus. The fixed allowance covers report/path setup, especially tiny inputs. The 13 corpus pairs use N=128 KiB and 4N=512 KiB (file/path counts scaled to fit all caps), and assert both sizes actually scan without size/file refusals. Nesting uses many balanced groups; a separate depth-60 case retains the depth stress. Timing uses five-run medians after warm-up; short scans repeat the same input in equal-size batches for N and 4N, with every measured N batch exceeding 1 ms. Work counts compare a single scan, independently of batching. Additional env/path-hunk/deep-nesting corpora use N=240 and 4N=960; the deep-nesting per-scan 4N ceiling is 300 ms. A separate four-file case exercises 4 MiB of actual scanning. Large refused paths are also checked for bounded fingerprint work.

This replaces the plan block's recorded-request ledger comparison for this lane. The ledger comparison, its F2/F3 dependencies and original 0.5.20 scheduling are deferred; no ledger or model call is built here. Deferred syntax includes other programming languages, semantic data flow, computed property names, YAML anchors/merges and semantic resolution of nonliteral expressions. A new language or grammar needs explicit tests and coverage rules before it can claim complete scanning.

`tests/fixtures/prompt-change/history.diff` is a README diff from repository commit `358ad1a0e` (captured with `git show --format= -- README.md`). The runtime-built fixtures contain no credential-shaped literals. All detector tests deny fetch and sockets. The no-callers test scans production packages; tests themselves are expected consumers.

TE-F3/TE-F10: diff input always has at best `hunks_only` coverage, so **both selectors always say needed for diff input**, even without detected items. Supply full before/after files to obtain complete coverage. The barrel exports the report/detector API only; raw-text diff parsers remain internal module imports. The strict parser rejects duplicate reasons/IDs, out-of-order items, and path fingerprints attached to safe or absent paths. It recomputes the digest for untruncated reports; for truncated reports the digest covers omitted items and cannot be verified from the displayed list alone.

## Limits

An unguarded `prompt:` key with no AI signal is conservatively reported as `prompt_text`. Spreads, `**kw`, and `create(params)` with no visible prompt can return `none_found` with complete coverage: the prompt text is not present in the supplied file. This detector does not follow variables or imports to find it.
